# DigitalArch

<!-- impeccable:product-schema 1 -->

## Platform

web

## Stack

React 19, Ant Design 6 compact, one Node.js ES-module backend, pnpm, PostgreSQL 16 + pgvector, local PNG filesystem storage. The existing Windows .NET 8 console helper uses NAPS2 SDK 1.6.0 and WIA through the WSL2 Windows bridge.

## Product Purpose

Digitize physical document bundles without mandatory metadata entry. An operator creates a batch, captures multiple feeder sessions, pauses/switches/resumes work across days, and explicitly completes capture. The system preserves identity, ownership, sequence, source provenance, originals and an audit trail.

## Operating Context

Desktop archive workstation, WSL2 backend and Windows browser/scanner driver. One backend/scanner installation with multiple authenticated accounts, not a distributed deployment. Scanner selection has no brand/model binding: Windows WIA devices and user/shared NAPS2 profiles are discovered, with an explicit portable-profile path override. The device-neutral application fallback uses simplex feeder, Letter, 300 dpi, color and right alignment; native profiles keep their own supported settings. Brother ADS-2400N is historical physical-test evidence, not a required scanner. Device detection is evidence, not a physical readiness claim.

## Capabilities and Constraints

PostgreSQL is authoritative for users, sessions, permissions and new capture workflow. Each batch represents one physical bundle and starts with one placeholder logical document; the schema permits future multiple documents. Physical location is optional and nonunique. Batch IDs are generated from Jakarta time plus a random suffix; actual identity is UUID. Display time is Asia/Jakarta; storage timestamps are UTC.

The active scanner contains exactly one batch or an explicit empty state. Scanning creates a sequential session, never another batch. Successfully registered pages from partial failures remain visible. Completing capture closes acquisition and queues OCR, but leaves optional document preparation editable. Only explicit Send to QC hands off and locks operator edits; QC must claim before corrections. Required batch versions, row locks and a one-running-session constraint prevent overwrites. Originals and feeder capture order are immutable. The provider spool is retained for idempotent recovery after registration/database failure.

The role-aware shell includes Operator Capture Workspace/My Batches/Scanner, OCR Processing, and Administration Users/Batch assignments/Audit Logs/System. System Administrator has no inherited capture privileges; OCR read/manage-all oversight is explicitly granted. Temporary-password onboarding, account disabling, role assignment, session revocation and permission enforcement are implemented. Capture/QC and approval roles, and the two approval levels, must remain separate.

The user's later instruction removed all legacy code/workflows: no global history, JSON QC registry/manifests or compatibility/import routes remain. Phase 4 uses the existing PostgreSQL capture/document records, not a second capture or OCR lifecycle. QC Officers have a real queue and document workstation. L1/L2 have read-only approval queues; working roles share the permission-scoped Documents registry. Approved Archive Viewers now have a separate published-only, image-only library described in [VIEWER.md](VIEWER.md).

Simulator is the startup capture default and its capture provider never touches Windows or hardware. Real scanning preserves profile discovery, capability evidence and the .NET helper; native profiles are read-only and unsupported processing options are not silently applied. There is no simulator fallback for hardware failure. Completed captures atomically queue PostgreSQL-backed OCR through the same Windows/.NET 8 helper and NAPS2.Sdk 1.6.0 Tesseract API. Best Indonesian and English resources are required by default. OCR is separate from capture state, runs at concurrency 1, persists text and bounds immediately, and supports pause/resume, bounded retries and lease-based recovery. Standard/enhanced/high-accuracy profiles, PSM 3/4/6 and sequential benchmark mode compare configurable preprocessing on temporary images, never the retained originals. Reprocess preserves prior results. Scanner resolution remains 300 DPI; higher accuracy is measured rather than guaranteed by preset names. Pre-feature completed captures have an explicit Send to OCR action; completed details hide acquisition controls. No AI extraction/classification, embeddings, cloud storage or distributed queue infrastructure is implemented. Image-only PDFs are limited to the approved Viewer workflow below. pgvector is enabled without an arbitrary vector dimension.

## Scanner discovery

Scanner mode/device/profile selection is isolated per operator account (shared across that account's browser tabs). Each real WIA device has an exclusive reservation and independent FIFO waiting queue. Operators reserve before loading paper; promotion never starts capture automatically. Idle ownership/queue entries expire after two minutes without authenticated scanner-status polling; sign-out releases them. Captures never expire and stay reserved until process settlement and page reconciliation, including unconfirmed stops. Different devices may capture concurrently; actual Windows/driver concurrency is not yet verified. Capability probes occur only in reserved capture, not discovery. Queues/selections are transient across backend restarts; durable unresolved-capture markers quarantine affected devices until explicit administrator recovery. The backend remains a single capture host with loopback-only deployment; secure laptop/LAN exposure is a separate task. OCR scheduling is unchanged.

Real Hardware inventory refreshes approximately every 30 seconds while its status is viewed, excluding acquisition. Scanner settings expose source files, native defaults, unsupported reasons and last detected additions/removals/setting changes. Initial selection prefers a unique native default or matched profile; ambiguous or removed selections cannot silently fall back. Stable native profile IDs and definition revisions pin capture settings through scan-time rechecks. Unsupported profiles remain visible, not silently translated; WIA is the supported driver path, not TWAIN. No native profile file is edited, and a scan-failure latch still requires explicit refresh. This discovery update has static/build verification only, without hardware queries or executed tests.

## Phase 4: document verification and rework

One batch initially represents one logical document across all feeder sessions. Optional document metadata is editable before OCR; automatic rule extraction retains human values and exposes source pages, available bounds, candidates and verification history. OCR-run metadata remains historical. Required metadata types are configured per document by an administrator, not imposed by a new mandatory capture form.

QC claims are exclusive, persistent, version-fenced and time-limited. A document's creator, assigned operator and every session's capture operator are excluded from reviewing it, including combined Administrator/QC accounts. Administrators may release claims with a reason but cannot bypass self-QC. QC checks include page review status, order/completeness checklists, findings, metadata verification and explicit terminal OCR exceptions.

Rotation, order, exclusion/restore, insertion and confirmed replacement preserve original images and capture provenance. Separate human OCR corrections never rewrite machine text. Returning to the assigned operator reopens the same batch; resubmission creates another review cycle without deleting prior decisions/findings. QC Pass verifies storage integrity and locks a snapshot at **Awaiting Approval Level 1**, fixing the batch's L1-only or L1→L2 policy. See [QC.md](QC.md) and [APPROVAL.md](APPROVAL.md) for the subsequent decisions and limits.

## Publication, viewer access and documentation boundary

Approvals reuse the reviewed snapshot, existing roles/session/audit infrastructure, shared `WorklistTable` and `PageViewer`. L1 explicitly publishes under the fixed L1-only policy or nominates L2, who must confirm publication. Returns create another QC cycle; whole-batch drops retain originals/history without publication. Independent L2 officers may take down a publication with a reason, returning it to a new QC cycle or to L1 with an explicitly carried-forward signed QC snapshot; either route requires fresh approvals under the fixed policy. Historical role participation remains disqualifying. Each confirmation has an authenticated QR receipt and assigned-operator notification/printing.

[APPROVAL.md](APPROVAL.md) records approval policy and scopes. The single staff Documents menu shows published records only, with advanced server-side filters; unpublished work stays in workflow queues and unsent work stays private. Publication also enables the separately approved Viewer library, never public access. Viewers self-register, wait for administrator approval and browse list/grid with closeable document tabs. Grid cards contain a low-resolution first-page cover, title and document date. Viewer APIs expose only basic metadata and saved page images. Current/selected/all-page image-only PDF downloads use audited, authenticated app-managed transfers with bytes/speed/duration/cancellation; there is no OCR text layer or whole-library export. Four separate append-only viewer audit tables feed the administrator Audit screen. QR links remain local. Embeddings/AI search and multi-document splitting remain out of scope. Approval/viewer runtime and rendered behavior remain unverified at the user's request.

[DND.md](DND.md), [ERD.md](ERD.md) and [DFD.md](DFD.md) document the current architecture, schema and flows with standard Mermaid. The latest queue/shared-UI/URL refinements remain runtime-unverified at the user's request; historical verification is qualified in [ENGINEERING_REPORT.md](ENGINEERING_REPORT.md).

Operator/QC/L1/L2 share a top-navbar bell and durable individual read/unread/view inbox. QC Pass informs OP/eligible L1; selected-L2 work and final publication/QR actions reach responsible staff. Returns, drops, takedowns and assignments are centralized instead of recurring workflow popups. PostgreSQL transactional audit triggers, indexed recipients and LISTEN/NOTIFY drive SSE without Redis, inbox polling or new services. Migration 019 is applied locally; runtime/rendered acceptance is unverified. See [NOTIFICATIONS.md](NOTIFICATIONS.md).

## Evidence on Hand

An explicit alternative OCR engine is available through the same OCR job/reprocessing workflow: PaddleOCR 3.7.0 with the verified PP-OCRv6 Small detector/recognizer, running on a project-local Linux/WSL Python CPU runtime. It supports Indonesian and English and preserves original PNGs and Tesseract history. The administrator Settings menu stores global OCR defaults in PostgreSQL, including supported 1/2/4-thread Paddle budgets (initially 1), languages, profile and preprocessing. New capture/enqueue/reprocess jobs snapshot defaults; existing jobs never inherit later setting changes. Page concurrency remains 1 and Tesseract remains the initial production default. Model/hardware details are in Settings and saved Job details; the redundant next-run strip is removed. Paddle adds no Docker image, Redis or separate service. Higher-thread speed claims require an explicitly approved benchmark; OCR verification must never be run without user approval. Existing benchmark evidence and resource limitations are in OCR.md.

The existing local `pgvector/pgvector:pg16-bookworm` image was inspected and reused, with no image download. PostgreSQL 16.15/vector 0.8.7 connectivity was verified through WSL Node.js. Automated checks exercise authentication, all six roles, administration, ownership, batch lifecycle, concurrency, simulation, files/checksums, recovery, strict CSP and three desktop viewport sizes.

The database-backed session completed, originals passed decoding/SHA-256 verification, and batch `B-20261113-115334-FB68BC7B` was paused.
